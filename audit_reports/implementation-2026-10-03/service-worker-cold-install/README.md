# Cold service-worker installation diagnosis and fix (ADD-09)

The final Chromium/Mobile Chrome integration run reproduced a 120-second timeout waiting for `navigator.serviceWorker.ready`. [The original failed trace retained only in temporary storage](/tmp/herdly-sw-failed-cold-install-trace.zip), [page context](failed-error-context.md) and [pre-fix browser log](pre-fix-browser-gate.log) are retained before the next Playwright run overwrites test-results. The raw Playwright trace can contain synthetic authentication request bodies/cookies and is intentionally kept only under `/tmp`; repository evidence includes the sanitized public shell URL/status/state/cache diagnostics and error context.

Fresh independent Chromium contexts against the actual production server reproduced the worker stuck in `installing` with an empty cache. CDP stage observation of the [served worker](served-worker-at-diagnosis.js) showed all three `/worker*` fetches return 200 headers, while `/manifest.webmanifest` never returned its headers. The installation awaited `Promise.all` of all responses before consuming any HTML body. [Native stage log](native-install-stall.log) records that barrier; executing the same cache operations in a page context was a [successful control](page-context-control.log).

In the same real worker context, consuming each returned response clone immediately allowed the manifest request to resolve and the worker to activate with cached entries ([clone-consumption contrast](immediate-clone-drain.log); [materialized-body contrast](immediate-materialized-body.log)). This supports a streaming response-consumption/backpressure stall in this cold browser request pipeline; it does not claim a general documented limit for every browser. Diagnostic scripts use disposable browser profiles/contexts, actual localhost fetch/cache APIs and stage wrappers. They do not run E2E globalSetup, authenticate real users, or write domain facts. Owned diagnostic profiles are deleted.

The source fix moves `shellAssets(response)` inside each shell fetch callback, reading each HTML clone as soon as its headers arrive. Original responses remain staged; all discovered hashed assets must still cache successfully before any new fallback HTML is published. Missing chunks continue to reject installation and preserve prior complete fallback. Late response cloning/waitUntil, network-only API behavior and bounded navigation fallback remain intact.

The new regression models a fourth response blocked until the three earlier streamed bodies are consumed. The previous all-headers barrier cannot finish that test; the revised install drains them, warms the referenced chunk, publishes the complete shell/manifest and calls skipWaiting. [All 17 service-worker execution tests](vitest.log), [scoped ESLint](eslint.log), and [full frontend typecheck](typecheck.log) pass. [Structured commands/source hashes](summary.json) bind these local checks.

The root-owned rebuilt source now passes all three [real production correction journeys](production-corrections.log) in 13.3s: Mobile Chrome cold offline completion/reload/reconnect/attribution and the English/Telugu simulation axe checks. The served `/sw.js` bytes match the revised source hash in `summary.json`. The complete three-browser matrix/full frontend integration remain pending. Prototype-assisted activation is retained as causal diagnosis; the actual revised-source browser journey supplies the final correction proof. No test timeout or offline-integrity assertion was weakened.
