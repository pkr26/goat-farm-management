## Findings requiring design or implementation decisions

### 1. Membership PIN provisioning can authorize a global account session — P1, high source confidence

The PIN reset preparation allows any live membership and expressly omits the affiliation eligibility used for password reset ([team.py:384](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/team.py:384), lines 384–411). Password reset, by contrast, rejects accounts that are not farm-provisioned, own a farm, or have another affiliation ([team.py:451](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/team.py:451), lines 451–491). PIN mutation locks the target User, sets the membership PIN, and revokes the User's global session generation, without applying those affiliation restrictions ([team.py:1332](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/team.py:1332), lines 1332–1354).

Successful worker login calls the ordinary `_issue_tokens` path ([auth.py:1354](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:1354), lines 1354–1370). The refresh session stores a User/family, and the access token carries the User and token version; neither binds the resulting session to the membership/farm that supplied the PIN ([auth.py:693](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:693), lines 693–741; [security.py:716](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/security.py:716), lines 716–742). Farm authorization subsequently selects any owned or active-member farm for the global User ([deps.py:460](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/deps.py:460), lines 460–573). This conflicts with the configuration/model statement that a PIN is scoped to one membership ([config.py:947](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:947), lines 947–950; [core.py:316](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/models/core.py:316), lines 316–320).

The normal farm-creation route also accepts `CurrentUser` and assigns that User ownership after validating its live token generation ([auth.py:2024](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:2024), lines 2024–2075). Thus a PIN account is not structurally restricted to remaining an isolated worker account. Source-defined scope is broader than the farm owner who can set the PIN. Active TOTP and `must_change_password` explicitly block worker PIN login ([auth.py:1337](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:1337), lines 1337–1353); this finding does not assert bypass of those checks. Actual cross-farm consequences require a PIN-eligible account with additional authority and without those blockers.

**Recommendation:** carry membership/farm scope in PIN-origin access and refresh sessions and enforce it throughout refresh and authorization. Until that design exists, apply the isolated-account affiliation eligibility consistently to PIN provisioning/rotation. Test the intended session scope across farm selection and refresh as a functional authorization invariant.

### 2. Production file-secret delivery mounts every service's secrets into every database-capable service — P1, high source confidence; deployment-dependent impact

The shared bind mount maps the entire `${GOATFARM_APP_SECRET_DIR:-./secrets/app}` directory into `/run/secrets/app` ([docker-compose.production.yml:36](/Users/pradeepreddy/Desktop/goat-farm-management-main/docker-compose.production.yml:36), lines 36–40). The migrator, API, and screening worker all receive it ([docker-compose.production.yml:112](/Users/pradeepreddy/Desktop/goat-farm-management-main/docker-compose.production.yml:112), lines 112–114; [line 224](/Users/pradeepreddy/Desktop/goat-farm-management-main/docker-compose.production.yml:224), lines 224–226; [line 303](/Users/pradeepreddy/Desktop/goat-farm-management-main/docker-compose.production.yml:303), lines 303–305). The documented adoption procedure puts database URLs, migration URL, HMAC/TOTP keys, storage/provider credentials, and MSG91 credentials in one directory, with files readable by container UID 10001 ([.env.example:115](/Users/pradeepreddy/Desktop/goat-farm-management-main/.env.example:115), lines 115–142). All three services use the backend image's UID 10001 ([Dockerfile:51](/Users/pradeepreddy/Desktop/goat-farm-management-main/Dockerfile:51), lines 51–53, 75).

Narrow settings/environment projections cannot prevent direct reads of files in the shared mount. When deployment follows the file-delivery instructions and colocates these secrets, the long-lived API/worker can read the migration credential and the migrator/worker can read API-only HMAC/TOTP material. Comments claiming the migrator receives no API secrets and the worker receives only its role's secrets ([docker-compose.production.yml:83](/Users/pradeepreddy/Desktop/goat-farm-management-main/docker-compose.production.yml:83), lines 83–85, 259–261) are accurate only for environment projection, not filesystem access. No actual deployed secret contents or deployment state were inspected.

**Recommendation:** mount individual files per service, or use separate service-specific secret directories. Keep DDL credentials outside long-lived API and worker containers, and API-only signing/encryption material outside the migrator and screening worker.

### 3. Account deletion retains identifiable notification phones and MFA credential material — P2, high source confidence

The deletion contract says it removes access and profile data while preserving pseudonymous operational attribution ([auth.py:1888](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:1888), lines 1888–1900). Its actual mutation deletes refresh sessions and replaces email/name/password while setting `deleted_at` and bumping token version; it does not clear MFA fields, recovery-code rows, membership PINs, or notification recipients ([auth.py:1974](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:1974), lines 1974–1984).

User TOTP secret/state/step fields remain on the tombstone ([core.py:76](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/models/core.py:76), lines 76–78). Recovery-code hashes have an `ON DELETE CASCADE`, but this endpoint updates rather than deletes User, so the cascade is not invoked ([core.py:98](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/models/core.py:98), lines 98–124). Notification recipients retain a phone linked to the membership ([notifications.py:62](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/models/notifications.py:62), lines 62–73), and the tombstone cleanup worker only sets memberships inactive ([deps.py:309](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/deps.py:309), lines 309–362). The inspected retention worker sources did not contain recipient/MFA scrubbing; that service was only partially read, as disclosed in the ledger.

Notification delivery correctly excludes deleted Users ([service.py:352](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/services/notifications/service.py:352), lines 352–365, 587–599). The issue is retained personal linkage and unnecessary dormant credential material, not continuing messages or usable deleted-account sessions.

**Recommendation:** clear bounded User MFA state during tombstoning and perform bounded post-deletion deletion/scrubbing of recovery codes, membership PIN material, and notification-recipient PII. Preserve the immutable User/membership IDs needed for attribution, and document any deliberate retention exception and duration.

### 4. Cadence materialization permanently restarts at the lowest farm IDs — P2, high source confidence

Every tick resets `after_farm_id = 0` inside the outer loop, then processes only `max_batches` pages ([main.py:503](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/main.py:503), lines 503–519). The service uses genuine increasing-ID keyset pagination and returns the last ID ([cadence.py:571](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/services/cadence.py:571), lines 571–615), but the next tick discards it. Defaults are batch 100 and max 10 ([config.py:718](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:718), lines 718–720).

Once farm count exceeds batch-size × max-batches, farms above the first 1,000 IDs under defaults never receive this sweep's recurring duties. The task-board GET is deliberately read-only, making this background loop the documented materialization path ([main.py:496](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/main.py:496), lines 496–501). This conclusion follows directly from the loop and does not rely on runtime reproduction.

**Recommendation:** retain a cursor across ticks and wrap only after exhaustion, while keeping each tick bounded. A functional test should exceed one tick's capacity and verify eventual service for higher IDs.

### 5. Three MFA management paths do not revalidate the authenticated session generation under their final User lock — P2, high source confidence; concurrency effect inferred

`CurrentUser` checks token version during its initial unlocked account read ([deps.py:174](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/deps.py:174), lines 174–197). TOTP enrollment and password change additionally snapshot the authenticated version and compare it under the eventual User write lock ([auth.py:2284](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:2284), lines 2284–2304; [auth.py:1697](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:1697), lines 1697–1767).

TOTP confirmation snapshots only User ID, reacquires the live User with `populate_existing`, and activates MFA/mints codes without the version comparison ([auth.py:2371](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:2371), lines 2371–2435). TOTP disable similarly snapshots only ID and loops across password verification's rollback before reacquiring the final lock ([auth.py:2457](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:2457), lines 2457–2492, 2553–2559). Recovery regeneration verifies a snapshotted password outside the transaction, then locks by live User ID and changes recovery material without a version comparison ([auth.py:2600](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:2600), lines 2600–2668). The shared confirmation helper does not carry/validate token version ([auth.py:2237](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:2237), lines 2237–2255).

A request authenticated before a concurrent password/session-generation revocation can therefore mutate MFA state after that revocation completes. Disable/regeneration still require their configured password/TOTP proofs; this is a lifecycle ordering inconsistency, not a claim that those proofs can be omitted. No race was reproduced.

**Recommendation:** capture the authenticated token version before rollback/ORM expiration and compare it under every final exclusive User lock. Consolidate this repeated lifecycle protocol so future routes do not omit the final check.

### 6. Hourly alert sweep is unbounded and marks the hour complete before processing farms — P2, high source confidence

The hourly path sets `last_sweep_hour` first, then loads every Farm with an unordered, unbounded query and calls three alert routines serially ([main.py:468](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/main.py:468), lines 468–477). Failure handling wraps the entire iteration rather than each farm ([main.py:478](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/main.py:478), lines 478–481). A propagated farm-level error stops the remainder and subsequent ticks within that hour skip the sweep. Repeated failures before a later farm can repeatedly defer its alerts. Database/domain/config errors can propagate even though individual transport delivery failures may be handled lower down.

The advertised `notifications_loop_batch_size` bounds farm scans ([config.py:942](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:942), lines 942–945), but only digest readiness applies that limit ([service.py:538](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/services/notifications/service.py:538), lines 538–549); the hourly sweep does not. This is both a resource-bound inconsistency and incomplete failure isolation.

**Recommendation:** use bounded keyset cohorts for the hourly routines, isolate/rollback per-farm errors, and advance a durable/completed cursor rather than treating the hour as complete before work. Retain idempotent day-based delivery deduplication.

### 7. The default secret mount directory is absent from Docker build-context exclusions — P2, high source confidence; exposure conditional

Production defaults to `./secrets/app` ([docker-compose.production.yml:38](/Users/pradeepreddy/Desktop/goat-farm-management-main/docker-compose.production.yml:38)); the directory is git-ignored ([.gitignore:34](/Users/pradeepreddy/Desktop/goat-farm-management-main/.gitignore:34), lines 34–37) but `.dockerignore` contains no `secrets/` exclusion ([.dockerignore:1](/Users/pradeepreddy/Desktop/goat-farm-management-main/.dockerignore:1), full 53 lines). Backend builds use the repository root context, including CI/release paths ([ci.yml:474](/Users/pradeepreddy/Desktop/goat-farm-management-main/.github/workflows/ci.yml:474); [release.yml:105](/Users/pradeepreddy/Desktop/goat-farm-management-main/.github/workflows/release.yml:105)).

If operators put secret files in that documented/default path, the directory is eligible for inclusion in the build context and access by build tooling/context archives. The Dockerfile's explicit COPY paths do not copy `secrets/` into the final image ([Dockerfile:41](/Users/pradeepreddy/Desktop/goat-farm-management-main/Dockerfile:41), lines 41–42, 55–62); no claim is made that a published image currently contains secrets.

**Recommendation:** exclude `secrets/` and all documented local secret-delivery paths from the Docker context, and prefer deployment secrets outside the checkout.

### 8. Production has no supported metrics opt-in and disables the collection itself — P3, high source confidence; operational policy tradeoff

Production validation overwrites `metrics_enabled=True` to False by design ([config.py:1610](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:1610), lines 1610–1618). This suppresses not just `/metrics` registration ([main.py:1053](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/main.py:1053), lines 1053–1062), but HTTP and maintenance observations/counters themselves ([metrics.py:87](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/metrics.py:87), lines 87–95, 139–176). The maintenance counters specifically intended to detect a silent background-worker death cannot be collected in production ([metrics.py:166](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/metrics.py:166), lines 166–172). Readiness checks only DB connectivity ([main.py:858](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/main.py:858), lines 858–869).

Structured logs and always-on auth-429 summaries still exist ([metrics.py:99](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/metrics.py:99), lines 99–109); this is not total absence of observability. Keeping an unauthenticated endpoint off is intentional, but there is no supported authenticated/private replacement for the maintenance telemetry.

**Recommendation:** separate metric collection from endpoint exposure and add authenticated/internal scraping, or provide an explicit mandatory production maintenance-progress/health signal with bounded labels.

## Smaller correctness and maintainability follow-ups

### 9. PIN-reset response computes password-reset permissions using the target as the actor — P3, high source confidence

`reset_pin` receives the reauthorized owner as `user`, but calls `_membership_out` with `locked_user`, the target worker ([team.py:1333](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/team.py:1333), lines 1333–1347, 1365–1369). `_membership_out` treats its User argument as the actor and overrides password-reset permission whenever that ID differs from the farm owner ([team.py:501](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/team.py:501), lines 501–505). Ordinary worker PIN-reset responses therefore report `can_reset_password=False` and the owner-only reason to the owner even when the underlying eligibility policy permits reset. Pass the acting `user` consistently.

### 10. Worker roster silently omits eligible workers above 100 — P3, high source confidence

The roster endpoint orders eligible active PIN workers and applies a fixed `.limit(100)` ([auth.py:1108](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/api/auth.py:1108), lines 1108–1137). Its response schema has only an `items` list, without pagination/overflow metadata ([schemas/auth.py:139](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/schemas/auth.py:139), lines 139–156). The supported default team cap is 200, configurable to 10,000 ([config.py:880](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:880)). Above 100 eligible workers, later rows are absent from this endpoint's selection result. Add pagination or reconcile the supported cap and surface truncation explicitly; no frontend behavior was reviewed here.

### 11. Production notification configuration permits a blank plain MSG91 key — P3, high source confidence

The production gate checks `msg91_auth_key is None`, not whether its content is nonblank ([config.py:1403](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:1403), lines 1403–1410). Provider creation uses the same None-only condition and forwards the string unchanged ([providers.py:122](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/services/notifications/providers.py:122), lines 122–131). An empty/whitespace plain-secret setting can therefore pass the intended boot-time credential requirement and fail delivery later. File-secret loading already rejects blank content ([config.py:325](/Users/pradeepreddy/Desktop/goat-farm-management-main/backend/app/core/config.py:325), lines 325–332). Use the existing nonblank-secret helper consistently for both delivery modes.

### 12. Release reruns update assets but can preserve stale published image digests — P3, high source confidence; conditional on changed build digest

The release workflow reuses an existing release and clobbers its SBOM assets on rerun ([release.yml:433](/Users/pradeepreddy/Desktop/goat-farm-management-main/.github/workflows/release.yml:433), lines 433–448). It fetches the current notes but writes newly produced backend/frontend digests only if the `Published image digests` heading is absent ([release.yml:451](/Users/pradeepreddy/Desktop/goat-farm-management-main/.github/workflows/release.yml:451), lines 451–461). If a rerun produces new image digests, the release can contain fresh assets/images with the old advertised digests despite the comment promising refreshed notes. Replace the workflow-owned digest block idempotently each run.

### 13. Applied-migration gate exemptions authorize all future edits to three filenames — P3, high source confidence

CI's `sanctioned` list names three migration files and exempts any modified/deleted/renamed entry with one of those paths ([ci.yml:91](/Users/pradeepreddy/Desktop/goat-farm-management-main/.github/workflows/ci.yml:91), lines 91–99). The comments explain past correction/docstring incidents and ask that one exemption be removed after the next push ([ci.yml:83](/Users/pradeepreddy/Desktop/goat-farm-management-main/.github/workflows/ci.yml:83), lines 83–90), but the implementation does not limit the exception to an approved diff, commit, or content digest. Unrelated future edits to those already-applied revisions silently pass the immutability gate. No current migration-behavior defect is inferred from this finding. Bound exceptions to the incident's exact content/commit, or retire them after the incident instead of relying on an enduring path allowlist.

## Positive controls and review limits

The reviewed sources contain substantial production fail-closed validation, bounded password/PIN CPU admission, token-generation checks on many lifecycle operations, explicit owner-only team credential mutation, refresh-session families and reuse handling, scoped permission normalization, database row/advisory locks, masked security logging, and no-email fallback in the unauthenticated worker roster. Those controls are part of the actual source and narrow several consequences above; they do not resolve the mismatches identified here.

The review did not inspect a running deployment, real credentials, production data, the frontend, or external provider behavior. Supplementary notification/retention/cadence/model files have the precise read ranges disclosed in the ledger. Recommendations are implementation directions, not performed fixes. Final source status was clean (`git status --short` empty).
