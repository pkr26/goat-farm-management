# Deep Audit — Goat Farm Management (2026-08-08)

**Scope:** 10 parallel lenses over the full monorepo, one calendar day after
the previous audit (`AUDIT.md`, 2026-08-07) was fully remediated in commit
`ade8096`. Each lens spot-checked prior fixes and hunted for **new** issues
— particularly regressions from the models/services package split.

**Verdict — headline numbers**

| Severity | Count | vs. prior audit |
|----------|-------|-----------------|
| CRITICAL | 0 | unchanged |
| HIGH     | 8 | (all newly discovered; prior 17 HIGH all verified as fixed) |
| MEDIUM   | ~20 | mostly ops-hardening + refactor gaps |
| LOW      | ~15 | polish |
| REGRESSIONS from split | **0** | the ade8096 split is clean |

Spot-checks of previous HIGH findings **all landed**: T1 refresh-session
family + reuse detection, T2/T6/T7 row-locking on ultrasound/abort/kidding,
T3 simulation cross-field validator, T4 deworming template match, T5
`/healthz`/`/readyz` + Docker + CI + prod-config validator, T8 structured
logging with request IDs. The multi-tenancy sweep produced **zero** new
findings — the split preserved every `farm_id` filter and ownership
re-check.

The eight new HIGH issues cluster in three areas that the prior audit did
not surface:

1. **Business-logic completeness** — health costs are silently absent from
   the P&L; lactating-doe sales orphan kids in RECOVERY.
2. **DB schema durability at scale** — money stored as `Float`, enums
   stored as bare `String` with no `CHECK`, and read-side hydration that
   loads the entire active herd for a dashboard page.
3. **Simulation edge case + prod-config gaps** — a sensitivity-mode input
   still crashes with `math domain error`; the in-memory rate limiter has
   no worker-count hard cap in the Dockerfile; Playwright is checked in
   but never runs in CI; no backup/DR plan exists.

There are **no exploitable cross-tenant, injection, or auth vulnerabilities.**
The auth layer, session lifecycle, and RBAC surface remain strong.

## Top New Findings (Ranked)

### N1. HIGH — Health event costs never enter the ledger
`backend/app/services/health.py:29-59`, cross-referenced against
`backend/app/services/finance.py` and every `TransactionCategory.*`
consumer.

`record_health_event` stores `cost` on the `HealthEvent` row but creates
**no** `Transaction`. `TransactionCategory.MEDICINE` and `.VET` exist in
`models/enums.py:73-74` but are never written by any service or API path
(grep-verified: `grep -rn "TransactionCategory\." backend/app` → schema
definitions and route parameters only, no writes).

**Real-world impact:** a farmer who records a ₹5,000 PPR round for 20
animals sees 20 HealthEvent rows with `cost=250` each — and a ₹0
"Medicine" line on that month's P&L. Monthly loss is systematically
understated. This has probably been happening for every user of the app.

**Fix:** in `record_health_event`, when `total_cost is not None`, add a
single `Transaction(type=EXPENSE, category=MEDICINE|VET, amount=total_cost,
date=event_date, related_animal_id=None)`. Vaccines → MEDICINE; treatments
with a vet visit → VET. Backfill for historical HealthEvent rows should be a
one-shot script rather than a migration.

### N2. HIGH — Selling or killing a lactating doe orphans her kids in RECOVERY
`backend/app/api/animals.py:382` (`skip_pending_tasks_for_animal`),
`backend/app/services/kidding.py:184-190` (WEANING task created with
`animal_id=doe.id`), `backend/app/services/feeding.py:71-75` (RECOVERY
treated as lactating).

When a doe is SOLD/DEAD, the animal-scoped WEANING task is SKIPped. Her
kids stay in `Bucket.RECOVERY` with no re-issued weaning task. The daily
feeding plan then keeps allocating the lactating recipe (RECOVERY = lactating)
even though the dam is gone. `days_in_current_bucket` climbs indefinitely;
nothing surfaces the anomaly to the farmer.

**Fix:** in the SOLD/DEAD/CULLED branch of `change_status`, look up ACTIVE
kids in RECOVERY where `dam_id == animal.id` and either move them to
MALE_KIDS/FEMALE_KIDS by sex, or re-assign a WEANING task to
`kidding_date + 60 days` with `animal_id=kid.id`. Preferred: move-by-sex,
which mirrors the natural weaning transition.

### N3. HIGH — `Transaction.amount` and `Animal.sale_price/purchase_price`, `HealthEvent.cost`, `Animal.weight_kg` all stored as `Float`
`backend/app/models/finance.py:26` (migration
`ed5efe13a516_initial_schema.py:361`), `models/animals.py:39,54,160`,
`models/health.py:35`.

Money is in binary float. The existing NaN/±inf filters in
`services/finance.py:27-33` are a symptom, not a fix. As transaction
volume grows, monthly rollups will drift cent-by-cent; the drift is silent.
Weight/price also have **no `CHECK` constraint** at the DB layer — Pydantic
is the sole guard against negative values.

**Fix:** `Numeric(12, 2)` for money, `Numeric(6, 2)` for weight, plus DB
`CHECK (amount >= 0)` / `CHECK (weight_kg > 0)` / `CHECK (bcs BETWEEN 1 AND 5)`.
Drop the finite guards. Migration is straightforward (`USING amount::numeric(12,2)`)
and cheap at current data sizes.

### N4. HIGH — Every enum stored as bare `String` with no DB-level `CHECK`
`Animal.sex/status/source/current_bucket`, `BreedingRecord.outcome`,
`Task.status/category`, `Transaction.type/category`, `KidEntry.status`,
`HealthEvent.type`, etc. (`backend/app/models/*.py`).

A stray `UPDATE animals SET status='sold'` (lowercase) or a `psql`
one-off edit corrupts every code path that compares against
`AnimalStatus.SOLD.value`. Every enum value string is duplicated in the
ORM, in code comparisons, and in `alembic/versions/ed5efe13a516_initial_schema.py`.
There is no single source of truth at the DB layer.

**Fix:** either Postgres `ENUM` types (typed once, migrations add values),
or `CheckConstraint(status.in_([...values...]))` generated per column from
`enums.py`. Either kills the risk of "casing bug" silently corrupting
production data.

### N5. HIGH — `list_animals` unpaginated + `dashboard()`/`buckets_board()` hydrate the entire ACTIVE herd
`backend/app/api/animals.py:124-128`, `api/dashboard.py:56-64`,
`api/buckets.py:24-30`.

The `limit=None` branch of `list_animals` returns the full active herd; at
50k animals per farm the JSON payload alone is ~50 MB and three
`selectin` follow-ups scan every id. `dashboard()` and `buckets_board()`
run `ANIMAL_OUT_LOADS` on **every** active animal only to render counts
(`counts[bucket] += 1`, `sex_counts[sex] += 1`). All of this is O(farm-age)
memory + latency per page render.

**Fix:**
- Make `list_animals` limit **mandatory**, default 200 / max 1000.
- Rewrite the count views as `SELECT current_bucket, sex, COUNT(*) GROUP BY …`
  (already the pattern in `reports()`), and pass only the small
  ready-to-move candidate subset through `ANIMAL_OUT_LOADS`.
- Add `CREATE INDEX ix_animals_farm_active ON animals(farm_id) WHERE status='ACTIVE'`
  and `ix_animals_farm_status_bucket` for the count-by-bucket query.

Also related: `Animal.tag_number ILIKE '%q%'` at `api/animals.py:122` uses
a leading wildcard and cannot use the unique btree; at 50k animals every
search is a seq scan. Add a `pg_trgm` GIN index on `tag_number` or reject
leading wildcards.

### N6. HIGH — Simulation sensitivity mutator crashes on `math domain error` for schema-valid inputs
`backend/app/simulation/montecarlo.py:163-165` mutates
`mortality.kid_pre_weaning` via `setattr` without `validate_assignment=True`.
Multiplier is 1.2; the schema allows `kid_pre_weaning ≤ 0.9`, so any
base value `> 1/1.2 ≈ 0.833` overflows past 1.0 and then
`engine.py:79` computes `math.pow(1.0 - 1.08, 1/12)` → `math.pow(-0.08, 1/12)`
→ `ValueError: math domain error` → uncaught → **500**.

Minimal repro: `POST /api/simulation/run` with `assumptions.mortality.kid_pre_weaning=0.9`
and `sensitivity=true`.

**Fix:** clamp in the sensitivity lambda, `min(0.9, v.mortality.kid_pre_weaning * 1.2)`,
matching the identical clamp already present in `_apply_draws`
(`montecarlo.py:53`). Same lambda needs `min(4.0, litter_size * 1.2)` — a
LOW variant of the same class.

Related latent bug — `adult_weight_doe_kg` below `weight_by_age_months[12]`
produces a monotonically **decreasing** weight curve (no crash, but every
downstream cost/revenue is nonsensical); add a `model_validator`
requiring `adult_weight_doe_kg >= max(weight_by_age_months[:13])`.

### N7. HIGH — Playwright never runs in CI + rate limiter has no worker hard cap
`.github/workflows/ci.yml` (job list); `Dockerfile:32` (CMD);
`backend/app/ratelimit.py:1-11` (in-memory, per-process).

CI runs ruff / mypy / pytest / vitest / pnpm audit / pip-audit and builds
the frontend — but `pnpm exec playwright test` never runs, despite 16 spec
files (1292 LOC) checked in under `frontend/e2e/`. The only thing that
exercises SPA + FastAPI + Postgres integration is not gated on PR.

Separately, the auth rate limiter is explicitly documented as per-process
("run exactly one uvicorn worker") — but the Dockerfile `CMD` does not
pass `--workers 1`, and nothing prevents an operator setting
`WEB_CONCURRENCY=4`. Limits then silently multiply by N.

**Fix:** add a `playwright` job with `pnpm exec playwright install --with-deps chromium && pnpm e2e`,
uploading traces on failure. Change Dockerfile CMD to
`exec uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
--timeout-graceful-shutdown 30` (also fixes the PID-2 SIGTERM issue —
`sh -c` currently swallows the signal).

### N8. HIGH — No backup / DR plan
Repo has **no** `pg_dump` script, no PITR guidance, no RTO/RPO statement.
`docker-compose.yml` mounts a named `pgdata` volume with no backup
sidecar. On disk failure or accidental `DELETE FROM animals` this project
cannot roll back.

**Fix:** commit `backend/scripts/backup.sh` (pg_dump piped through gzip +
optional `aws s3 cp`) and a README "Backups" section with an explicit
RTO/RPO commitment (e.g. RTO ≤ 4h, RPO ≤ 24h). Enable WAL archiving in
`postgresql.conf` for point-in-time recovery.

### Lens 5 — DB Schema, Migrations, Query Performance

- **MED — All `DateTime` columns are timezone-naive** (`core.py:28,45,71,

- **MED — `Animal.dam_id/sire_id` no `ondelete`** — mismatch with the app's

- **MED — `Task` lacks composite `(farm_id, status, due_date)` index** —
  every dashboard/tab query filters exactly that trio.
- **MED — `monthly_pnl` fetches all-time rows then slices in Python**

- **LOW — many hot columns unindexed**: WeightRecord.date, HealthEvent.date,
  BreedingRecord.breeding_date/expected_kidding_date, KiddingRecord.doe_id,
  Transaction.related_animal_id.
- **LOW — future migrations should switch to `CREATE INDEX CONCURRENTLY`**
  once tables exceed a few hundred thousand rows.

### Addendum A — Auth & Session Deep Dive (second pass)

Files read in full: `security.py`, `api/auth.py`, `deps.py`, `core/config.py`,
`main.py`, `ratelimit.py`, `utils.py`, `api/team.py`, `models/core.py`.

**Verified clean (second pass):**
- `jwt.decode` called from exactly one place (`security.py:198-208`), always
  with a specific `expected_kind` and an explicit `algorithms=[...]` list.
- Every `logger.*` call in auth code uses `%s`-style placeholders, and all
  user-controlled values (client IP, email) are normalized before logging.
- Rate limiter uses `time.monotonic()` (never backwards, no wrap), prunes
  emptied deques from its map (`ratelimit.py:47-51`), and reset semantics
  are correct.
- Password-change interleave: `revoke_user_sessions` UPDATE + concurrent
  refresh's SELECT FOR UPDATE serialize at the row level; the outcome
  ("new token issued but immediately revoked on next use") is a UX papercut,
  not a security hole.

**New findings — all LOW/MED**

- **[NEW MED] — `RefreshSession` table has no expiry pruning.** Rows persist
  forever (per-user × per-login × 14 days retention). At 100 workers × 5
  logins/day × 365 days that's 182k rows/year just for one small farm's team.
  Queries by `jti` stay fast on the unique index, but the table bloats and
  vacuum burden grows. **Fix:** a lightweight periodic cleanup
  (`DELETE FROM refresh_sessions WHERE expires_at < NOW() - INTERVAL '30 days'`)
  scheduled from a `lifespan` background task or an external cron.

- **[NEW MED] — No account deletion path (GDPR / right-to-be-forgotten).**
  There is no endpoint to delete a user, only to deactivate a *membership*.
  A user who leaves their last farm has no way to remove their PII.
  `RefreshSession.user_id` cascades on user delete (`models/core.py:122`)
  but `Farm.owner_id` and `FarmMembership.user_id` have no `ondelete`, so
  the DELETE would fail. **Fix:** DELETE account endpoint + tombstone or
  cascade path for owner farms (with an explicit "transfer ownership first"
  guard).

- **[NEW LOW] — PyJWT default `leeway=0`.** No clock-skew tolerance
  (`security.py:201-203`). If the API server and a potential future auth
  server drift by even a second, tokens issued microseconds ago can 401.
  **Fix:** `jwt.decode(..., leeway=60)`.

- **[NEW LOW] — RS256 key size 2048** (`security.py:118`). Meets current NIST
  minimum; 3072 is the recommended floor for keys expected to live > 5 years.
  **Fix:** `key_size=3072` on next key rotation.

- **[NEW LOW] — `_dummy_password_hash` cold-start asymmetry.** First
  unknown-email login pays an Argon2id `hash()` cost (~200ms at default
  params) that a warm process doesn't. Detectable statistically. **Fix:**
  precompute in `create_app()` startup.

- **[NEW LOW] — `create_worker` runs 4 sequential queries** where 1 aggregate
  would do (see architecture Lens finding LOW-2). Latent latency, not
  correctness.

**Verified prior fixes** — all landed and correct: RS256 alg-pinning
(`security.py:202`), key file mode 0o600 (`security.py:126`), refresh session
+ family + reuse detection (`api/auth.py:262-278`), timing-equalized login
(`api/auth.py:225-236`), flock-serialized key generation
(`security.py:149-152`), peer-manager guard (`api/team.py:88-100`), generic
cross-farm refusal (`api/team.py:35, 174-212`), password-reset scope guard
(`api/team.py:293-350`), production config validator (`core/config.py:86-108`).

### Addendum B — Frontend Deep Dive (second pass)

**State / data**

- **[NEW MED] — Farm switching has a stale-in-flight response window.**
  `auth-context.tsx:63-73` runs `queryClient.clear()`, then sets

  old `X-Farm-Id` on the wire; when they resolve, TanStack Query re-inserts
  them under their (path-based) query key into the now-fresh cache, so the
  UI can flash previous-farm data for a moment. Not a security leak
  (backend returns data scoped to the header sent), but a UX bug. **Fix:**
  include `farmId` in every generated Orval `queryKey` (Orval supports a
  `queryOptions` mutator) OR change `selectFarm` to `queryClient.cancelQueries()`
  → set farm-id → `queryClient.clear()`.

- **[NEW LOW] — `queryClient.clear()` on farm switch also drops in-flight
  mutations.** Rare in practice (users usually finish a form before
  switching farms), but if a mutation was pending, its promise still
  resolves but the resulting cache write is lost. **Fix:** as above.
